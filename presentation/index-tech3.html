와썹하우스는 모임을 소개하는 계정에서 출발해, 반복 운영과 데이터 기반 확장이 가능한 웹 서비스로 바뀌고 있습니다.

TECH 01

기술 포인트 1: EAV 구조의 동적 신청폼

게더링마다 다른 질문을
코드 수정 없이 운영자가 직접 구성합니다.

01 ADMIN

질문 빌더

질문 타입, 필수 여부, 선택지, 노출 순서를 관리자에서 설정합니다.

02 SCHEMA

동적 렌더링

프론트는 서버에서 받은 폼 스키마를 기준으로 신청 화면을 만듭니다.

03 ANSWER

답변 저장

사용자의 답변은 질문 ID와 값의 조합으로 저장되어 게더링별 확장성을 가집니다.

04 MATCHING

자동매칭 확장

일부 질문은 매칭 필드가 되어 우연한 식탁 그룹 추천의 입력값이 됩니다.

TECH 02

기술 포인트 2: AI 에이전트와 멀티 에이전트 환경

반복 구현보다 중요한 것은
에이전트가 일관된 기준으로 협업하는 환경이었습니다.

기획 에이전트

요구사항 분해

게더링 운영 흐름을 사용자 기능, 관리자 기능, 예외 케이스로 나누어 작업 단위를 명확히 했습니다.

구현 에이전트

코드 생성과 수정

디자인 시스템, API 계약, 기존 컴포넌트 구조를 기준으로 프론트 기능을 빠르게 반복 구현했습니다.

리뷰·QA 에이전트

검증과 회귀 방지

UI 흐름, 인증 예외, 신청 상태, 관리자 액션을 분리해서 검토하며 배포 전 안정성을 높였습니다.

TECH 03

기술 포인트 3: 생성형 AI 기반 자동 번역

외국인 대상 게더링 확장을 위해
LLM 번역 파이프라인을 백엔드에 연결했습니다.

01 SERVICE

GMS API 연결

SSAFY GMS의 OpenAI 호환 API를 사용해 브라우저 번역보다 자연스러운 다국어 문장을 생성했습니다.

02 TRIGGER

저장 후 자동 번역

게더링 제목과 소개가 생성·수정되면 커밋 이후 번역 이벤트를 발행하고 비동기로 처리했습니다.

03 LOCALE

4개 언어 제공

한국어 원문을 영어, 일본어, 중국어, 스페인어로 번역해 외국인 사용자가 같은 게더링 정보를 읽을 수 있게 했습니다.

04 OPERATE

운영 안정성

원문 해시로 중복 번역을 줄이고, 관리자가 수정한 번역은 덮어쓰지 않으며 실패 시 한국어 원문으로 폴백합니다.

NEXT TECH

앞으로 도입하고 싶은 기술

검색·추천 품질과 배포 안정성을
서비스 성장 단계에 맞게 고도화하려고 합니다.

Elasticsearch
검색·추천 품질 고도화

현재 한계

게더링·리뷰·회원 검색이 관계형 DB의 LIKE 부분 일치 질의에 의존해 데이터가 늘수록 풀스캔으로 느려지고, 한글 형태소 분석·오타 보정·다국어 검색 품질도 제한됩니다.

도입 효과

역색인 기반 전문 검색과 Nori 분석기, 동의어·오타 보정으로 취향 기반 탐색 품질을 높이고, 관심사·자기소개 텍스트 색인과 향후 벡터 검색으로 매칭 후보 탐색을 가속합니다.

Kubernetes
배포·확장 안정성

현재 한계

Dockerfile, docker-compose, GitHub Actions 기반 단일 인스턴스 배포 구조라 모임 오픈 시점의 신청 폭주에 대한 오토스케일, 무중단 배포, 장애 자동 복구 수단이 부족합니다.

도입 효과

HPA로 트래픽 폭주 구간에 파드를 자동 증설하고, 롤링 배포와 셀프힐링으로 다운타임을 줄입니다. 매칭·알림 같은 배치성 작업도 API 트래픽과 분리해 안정적으로 운영할 수 있습니다.

RETROSPECTIVE

팀원 회고

신재령

기획이 바뀔 때마다 화면만 고치는 것이 아니라, 운영 흐름 전체를 다시 보게 됐습니다. 사용자 경험과 관리자 경험을 동시에 설계하는 일이 가장 어려웠지만, 덕분에 진짜 서비스는 신청 이후의 운영에서 완성된다는 걸 배웠습니다.

김태정

인스타와 구글폼으로 하던 일을 웹으로 옮기면서 데이터 구조의 중요성을 체감했습니다. 동적폼, 매칭, 관리자 기능이 연결되기 시작하니 제품의 확장성이 보였고, AI 에이전트와 함께 개발하면서 팀의 속도와 검증 방식도 함께 바뀌었습니다.
